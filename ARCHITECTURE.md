# Архитектура узла

## 1. Общая схема

Узел — один процесс Python (asyncio, один поток событий). Сеть из `N` узлов — `N` независимых
процессов, у каждого свой каталог состояния, Ed25519-ключ, TCP-порт, таблица маршрутизации,
DHT-хранилище, журнал и управляющий порт.

```text
                    ┌──────────────────────────────────────────────┐
  консоль (cli.py)  │ User Interface: run / shell / ctl            │
  управляющий порт ─┤ node/control.py (JSON-строки, токен, 127.0.0.1)│
                    └──────────────┬───────────────────────────────┘
                                   │ фасад Node: join, lookup_node, put_record, get_record,
                                   │ build_tunnel, send_via_tunnel, close_tunnel, get_network_state
   ┌───────────────────────────────┼───────────────────────────────────────┐
   │ Application Services          │                                       │
   │ app/messaging.py: разрешение получателя (FIND_VALUE), туннель,        │
   │ E2E TLS 1.3 поверх туннеля, APP_MESSAGE/APP_ACK, message_id, история  │
   ├───────────────────────────────┬───────────────────────────────────────┤
   │ Tunnel Management             │ DHT and Discovery                     │
   │ tunnel/manager.py:            │ routing/: XOR, Contact, k-bucket,     │
   │ BUILD/OK/FAIL, DATA/ACK,      │   RoutingTable, RoutingManager (LRU)  │
   │ CLOSE, состояния, контроль    │ rpc/dht_rpc.py: PING, FIND_NODE,      │
   │                               │   STORE, FIND_VALUE                   │
   │                               │ dht/: lookup, NodeRecord, хранилище   │
   ├───────────────────────────────┴───────────────────────────────────────┤
   │ Identity and Security                                                  │
   │ identity/: Ed25519, NodeID = SHA-256("ed25519"‖0x00‖pk), сертификат   │
   │ security/tls.py: SECURE_HELLO, TLS 1.3 mTLS, привязка к NodeID         │
   ├────────────────────────────────────────────────────────────────────────┤
   │ Transport                                                              │
   │ protocol/: кадр 24 байта + payload, MessagePack-схемы                  │
   │ transport/: TCP-сервер и клиент, пул соединений, Connection (декодер,  │
   │ RPC по request_id, Dispatcher по type), тайм-ауты                      │
   └────────────────────────────────────────────────────────────────────────┘
   Metrics and Experimentation: metrics/events.py (node.log + events.jsonl, счётчики),
   experiment/ (оркестратор процессов, сценарии, статистика, TCP-tap -> pcap)
```

Зависимости направлены сверху вниз. Прикладной слой не обращается к k-bucket и хранилищу
напрямую — только через фасад `Node`. Обработчики RPC не читают сокет и не разбирают
заголовок: `Connection` передаёт им уже проверенный по схеме payload.

## 2. Подсистемы

| Подсистема | Модули | Ответственность |
|---|---|---|
| Transport | `protocol/frame.py`, `protocol/codec.py`, `protocol/messages.py`, `transport/` | кадрирование, потоковый декодер, сериализация, строгие схемы payload, соединения, тайм-ауты, корреляция RPC, диспетчеризация по `type` |
| Identity and Security | `identity/identity.py`, `security/tls.py` | генерация и хранение ключа, `NodeID`, самоподписанный сертификат, рукопожатие TLS 1.3 с привязкой к `NodeID`, `session_id` |
| DHT and Discovery | `routing/`, `rpc/dht_rpc.py`, `dht/` | XOR-метрика, 256 k-bucket, проверка LRU перед вытеснением, bootstrap, refresh, итеративный lookup, подписанные записи, хранение, TTL, republish, репликация |
| Tunnel Management | `tunnel/manager.py` | построение туннеля с подписанными подтверждениями, пересылка ячеек, подтверждения и зонды, состояния `BUILDING/ACTIVE/DEGRADED/CLOSING/DEAD`, закрытие |
| Application Services | `app/messaging.py` | текстовые сообщения, E2E TLS-сессия, автоматическое восстановление туннеля, дедупликация, история |
| Metrics and Experimentation | `metrics/events.py`, `experiment/` | журнал событий, счётчики, запуск сети процессов, сценарии отказов, CSV/JSON, pcap |
| User Interface | `cli.py`, `node/control.py` | запуск узла, интерактивная консоль, одиночные команды |

## 3. Четыре графа

Работа строго различает:

1. **Underlay** — все узлы работают на `127.0.0.1` одного компьютера, каждый на своём порту.
   IP-достижимость полная: любой процесс может открыть TCP-соединение с любым портом.
   Ограниченный underlay (несколько сетей, namespaces, `nftables`) на упрощённом уровне не
   требуется и не моделируется.
2. **Bootstrap-граф** — какие адреса узел получает при запуске (`BOOTSTRAP_PEERS`). `star`:
   все узлы знают только узел 1; `ring`: узел `i` знает только узел `i-1`. Это **схемы
   начального подключения**, а не физические топологии — физически связность полная.
3. **DHT-overlay** — контакты, реально находящиеся в k-bucket после присоединения и refresh.
   Сохраняется в `routing_table.json` каждого узла и в `tables.json` каждого прогона.
4. **Туннельный маршрут** — инициатор → R1 → R2 → получатель. Ретрансляторы выбираются
   случайно из собственной таблицы инициатора; фактический путь подтверждается подписями
   каждого хопа и пишется в журнал (`tunnel.active route=...`).

Путь DHT-поиска (кого опрашивал lookup) туннелем не считается.

## 4. Основные потоки

**Присоединение (`join`).** PING каждому адресу из `BOOTSTRAP_PEERS` (если указан `NodeID@адрес`
— с проверкой `NodeID`) → self-lookup (поиск собственного `NodeID`) → refresh bucket дальше
ближайшего соседа → публикация собственной подписанной записи на `R = 3` ближайших узлах.
Результат — `bootstrap.json`.

**Lookup.** `Lookup` берёт `k` ближайших контактов из своей таблицы и итеративно опрашивает
до `ALPHA = 3` неопрошенных кандидатов из окна `k` ближайших. Контакты из ответов становятся
кандидатами поиска, но в таблицу попадают только узлы, которые сами ответили (непосредственно
наблюдённые). Подробно — [PROTOCOL.md §6.3](PROTOCOL.md#63-итеративный-lookup).

**Публикация записи.** `publish_self` создаёт `NodeRecord` с новым `sequence_number`,
`put_record` находит lookup'ом `k` ближайших к ключу узлов и отправляет `STORE` трём; успех —
не менее 2 подтверждений. Каждые `REPUBLISH_INTERVAL_S = 90 с` (≤ TTL/2) запись публикуется
заново; если подтверждений меньше `R`, публикация повторяется каждые 5 с. Узел, впервые
узнавший о контакте из `R` ближайших к ключу хранимой записи (даже если тот не поместился в полный
bucket), сразу передаёт ему эту запись — иначе присоединившиеся позже ближайшие узлы не имели бы её
до переопубликования.

**Отправка сообщения.**

```text
send(NodeID, текст)
  └─ ensure_session(NodeID)                     — нет живой E2E-сессии?
       ├─ resolve: FIND_VALUE(SHA-256("node:"‖NodeID)) → проверенная запись → адрес и ключ
       ├─ build_to: 2 случайных ретранслятора из таблицы → TUNNEL_BUILD по цепочке
       │     ← TUNNEL_BUILD_OK с подписанными подтверждениями всех хопов
       └─ E2E TLS 1.3 (SECURE_HELLO + рукопожатие) поверх байтового потока туннеля
  └─ APP_MESSAGE(message_id, ...) внутри E2E TLS → APP_ACK(delivered | duplicate)
```

Ретрансляторы пересылают ячейки `TUNNEL_DATA`, в которых лежат байты TLS-записей E2E-сессии,
поэтому прикладной текст им недоступен. Межузловые соединения при этом тоже защищены своим
TLS 1.3 (hop-by-hop), то есть содержимое сообщений зашифровано дважды.

**Отказ ретранслятора.** Получатель подтверждает каждую ячейку `TUNNEL_ACK`, инициатор при
простое шлёт пустые ячейки-зонды раз в секунду. Разрыв канала к соседу → `TUNNEL_CLOSE` с
`failed_node_id` идёт к инициатору → `DEAD`; зависший ретранслятор (без разрыва TCP) → нет
подтверждений 2 с → `DEGRADED`, ещё раз → `DEAD`. Для получателей, с которыми велась переписка,
`MessagingService` сразу строит новый туннель, исключая отказавший узел (если он неизвестен —
все ретрансляторы погибшего туннеля), и устанавливает новую E2E-сессию. Неподтверждённое
сообщение отправляется повторно с тем же `message_id`, получатель распознаёт повтор.

## 5. Инженерные решения

| Решение | Альтернативы | Почему так |
|---|---|---|
| Python 3.10 + asyncio | Go, Rust, потоки | в стандартной библиотеке есть TLS 1.3 (`ssl`), asyncio даёт тысячи одновременных соединений в одном потоке без гонок данных; скорость Python достаточна для `N = 15` |
| Независимые процессы на `127.0.0.1` | Docker Compose, network namespaces | на учебной машине (Windows) нет Docker и namespaces; процесс-узел имеет отдельные ключ, порт, таблицу, хранилище, журнал и жизненный цикл, как требует раздел 14 ТЗ |
| MessagePack | JSON, CBOR, Protocol Buffers | двоичные поля без base64: payload на 25–30 % меньше JSON (CBOR — того же размера); кодирование в 6–80 раз быстрее JSON и в 3–16 раз быстрее CBOR (`cbor2`), замер — `docs/serialization_benchmark.json`; схема описывается в коде, генерация кода не нужна |
| Строгие схемы payload, неизвестные поля запрещены | «терпимый» разбор | меньше поверхность атаки; все ограничения длины проверяются до использования данных |
| Ed25519 | ECDSA P-256, RSA | короткие ключи (32 байта) и подписи (64 байта), детерминированные подписи, поддержка в TLS 1.3 и `cryptography` |
| TLS 1.3 через `ssl`, доверие ровно одному закреплённому сертификату | собственный AKE (продвинутый уровень), CA | упрощённый уровень требует TLS 1.3 mTLS; сертификат самоподписан, но принимается только если его ключ хэшируется в ожидаемый `NodeID` |
| Переиспользование соединений (пул по адресу) | соединение на каждый RPC | одно TLS-рукопожатие на пару узлов вместо одного на запрос; RPC и туннельные ячейки мультиплексируются по `request_id` и `tunnel_id` |
| Контакты в таблицу — только после непосредственного ответа | добавлять всё, что пришло в `FIND_NODE_RESPONSE` | чужой ответ не может «наполнить» таблицу несуществующими узлами |
| Source-routed туннель с подписанными подтверждениями | телескопическое построение (Tor) | проще и укладывается в типы `TUNNEL_BUILD/OK/FAIL`; подписи хопов дают проверяемый журнал фактического маршрута |
| E2E TLS 1.3 поверх байтового потока туннеля | шифрование каждого сообщения отдельно | рекомендация ТЗ для упрощённого уровня; повторно используется та же проверенная реализация рукопожатия |
| Случайный выбор ретрансляторов (`SEED` в конфигурации) | выбор по рейтингу | рейтинг — требование продвинутого уровня; seed делает прогоны воспроизводимыми |

## 6. Конфигурация и состояние

Все параметры (`NODE_ID_BITS`, `K_BUCKET_SIZE`, `ALPHA`, `REPLICATION_FACTOR`, TTL,
интервалы refresh и republish, тайм-ауты, число хопов, пороги деградации, ограничения кадров
и сообщений) задаются JSON-файлом, переменными окружения или `--set` без правки кода
(`overlay/config.py`). Итоговая конфигурация пишется в `effective_config.json`.

Состояние узла: `identity_ed25519.pem` (закрытый ключ, PKCS#8), `tls_cert.pem`,
`routing_table.json`, `storage.json`, `record_seq.json` (монотонный номер собственной записи
переживает перезапуск), `lookups.jsonl`, `messages.jsonl`, `logs/`. Каталоги состояния
исключены из git.

## 7. Тестовый оркестратор

`overlay/experiment/cluster.py` запускает узлы как процессы `python -m overlay run --config ...`,
по одному с паузой 0,3 с, и ждёт `joined` каждого через управляющий порт. Оркестратор знает все
`NodeID` (читает `control.json`), чтобы выбирать пары «инициатор — цель», но рабочие узлы
этой информации не получают: узлу передаются только адрес(а) bootstrap-контакта и, в
контрольном испытании, `NodeID` цели конкретного запроса. Отказы моделируются `kill`
(аварийное завершение процесса), штатной остановкой и `freeze` (узел перестаёт обрабатывать
входящие кадры, TCP-соединения остаются открытыми — «зависание»).

pcap снимается `experiment/tap.py`: TCP-прокси между узлами записывает переданные байты как
синтетические Ethernet/IPv4/TCP-пакеты с корректными контрольными суммами и номерами
последовательности. Захват на уровне драйвера (Npcap, Wireshark) на машине не установлен.

## 8. Ограничения

- Один компьютер: задержки сети ≈ 0, измеренные времена отражают обработку в узлах, а не
  распространение сигнала; эффекты потерь и задержек (`netem`) не исследуются.
- На Windows подключение к закрытому порту на `127.0.0.1` отклоняется не сразу, а примерно
  через 2 с (стек повторяет SYN). Поэтому lookup с отключённым промежуточным узлом и
  `FIND_VALUE` после отказа хранителя занимают ≈ 2 с — это время обнаружения отказа
  стеком ОС, а не алгоритмом.
- Модель угроз не включает глобального наблюдателя, Sybil- и Eclipse-атаки, сокрытие размеров
  и времени пакетов (раздел 11.1 ТЗ).
- Псевдонимы (`alias`), передача файлов, пул туннелей и рейтинг ретрансляторов относятся
  к продвинутому уровню и не реализованы.
