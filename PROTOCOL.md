# Спецификация протокола, версия 1

## 1. Общие положения

- Транспорт — TCP. Все многобайтовые целые в заголовке — в сетевом порядке байтов (big-endian).
- Каждое TCP-соединение — поток кадров. Чтение из сокета не совпадает с границами кадров:
  декодер накапливает байты и выдаёт кадр, только когда получены заголовок и payload целиком.
- Payload — MessagePack-карта (map) со строковыми ключами по схеме типа сообщения (§5).
- В режиме `SECURITY_MODE=tls` поток кадров идёт внутри TLS 1.3 после открытого обмена
  `SECURE_HELLO` / `SECURE_HELLO_ACK` (§8). В режиме `plain` (этапы 1–2) — открыто.
- Время — миллисекунды Unix UTC (`u64`). `NodeID`, ключи хранения — 32 байта.

## 2. Формат кадра

```text
 0       1       2               4                              20              24
 +-------+-------+---------------+------------------------------+---------------+------------
 |version| type  |    flags      |          request_id          |payload_length | payload ...
 |  u8   |  u8   |     u16       |           16 байт            |     u32       | 0..65536 байт
 +-------+-------+---------------+------------------------------+---------------+------------
```

| Поле | Размер | Правило |
|---|---:|---|
| `version` | 1 | `1`; иное значение → `ERROR BAD_VERSION` и закрытие соединения |
| `type` | 1 | код из §3; неизвестный → `ERROR UNKNOWN_TYPE` и закрытие |
| `flags` | 2 | в версии 1 зарезервировано и равно `0` (направление однозначно задаётся типом); иное → `ERROR BAD_FLAGS` |
| `request_id` | 16 | случайные байты `os.urandom`; ответ несёт `request_id` запроса |
| `payload_length` | 4 | длина payload; больше `MAX_FRAME_PAYLOAD = 65536` → `ERROR FRAME_TOO_LARGE` и закрытие **до** приёма payload |
| `payload` | переменный | MessagePack по схеме типа |

Заголовок — `struct.Struct("!BBH16sI")`, 24 байта.

### 2.1. Обработка некорректных кадров

| Ситуация | Реакция |
|---|---|
| получено меньше 24 байт заголовка | ждать данных; сообщение не создаётся |
| заголовок получен, payload неполный | ждать данных; буфер под payload не выделяется сверх фактически полученного |
| несколько кадров в одном чтении | разбираются по очереди в порядке поступления |
| `payload_length > MAX_FRAME_PAYLOAD` | проверяется сразу после 24 байт заголовка: `ERROR FRAME_TOO_LARGE`, закрытие |
| неверная версия, неизвестный тип, ненулевые флаги | `ERROR BAD_VERSION / UNKNOWN_TYPE / BAD_FLAGS`, закрытие |
| payload не разбирается как MessagePack, ext-типы, превышение глубины | `ERROR DECODE_ERROR`, закрытие |
| нарушение схемы: нет поля, лишнее поле, неверный тип или длина | `ERROR SCHEMA_ERROR`, закрытие |
| ответ (PONG, `*_RESPONSE`, ...) без ожидающего запроса с тем же `request_id` | `ERROR UNEXPECTED_RESPONSE`, закрытие; ожидающий запрос не завершается |
| ответ не того типа, что ожидается на запрос | `ERROR BAD_DIRECTION`, закрытие |
| разрыв соединения внутри кадра | частичный кадр отбрасывается, ожидающие RPC завершаются ошибкой `closed`, ресурсы освобождаются |
| нет ответа за `READ_TIMEOUT_MS` | RPC завершается ошибкой `timeout`; соединение остаётся открытым |

После ошибки формата поток рассинхронизирован, поэтому соединение всегда закрывается; сервер
продолжает принимать новые соединения. `ERROR` без ожидающего запроса считается уведомлением
и только журналируется.

## 3. Типы сообщений

| Код | Тип | Направление | Ответ | Этап |
|---:|---|---|---|---|
| `0x01` | `PING` | запрос | `PONG` | 1–2 |
| `0x02` | `PONG` | ответ | — | 1–2 |
| `0x03` | `FIND_NODE_REQUEST` | запрос | `FIND_NODE_RESPONSE` | 2 |
| `0x04` | `FIND_NODE_RESPONSE` | ответ | — | 2 |
| `0x05` | `STORE_REQUEST` | запрос | `STORE_RESPONSE` | 3 |
| `0x06` | `STORE_RESPONSE` | ответ | — | 3 |
| `0x07` | `FIND_VALUE_REQUEST` | запрос | `FIND_VALUE_RESPONSE` | 3 |
| `0x08` | `FIND_VALUE_RESPONSE` | ответ | — | 3 |
| `0x09` | `SECURE_HELLO` | начало защищённой сессии (открыто) | `SECURE_HELLO_ACK` | 4 |
| `0x0A` | `SECURE_HELLO_ACK` | ответ | — | 4 |
| `0x10` | `TUNNEL_BUILD` | запрос | `TUNNEL_BUILD_OK` или `TUNNEL_BUILD_FAIL` | 5 |
| `0x11` | `TUNNEL_BUILD_OK` | ответ | — | 5 |
| `0x12` | `TUNNEL_BUILD_FAIL` | ответ | — | 5 |
| `0x13` | `TUNNEL_DATA` | ячейка туннеля (в обе стороны) | `TUNNEL_ACK` от получателя | 5 |
| `0x14` | `TUNNEL_ACK` | подтверждение ячейки (к инициатору) | — | 5 |
| `0x15` | `TUNNEL_CLOSE` | уведомление о закрытии/отказе | — | 5 |
| `0x20` | `APP_MESSAGE` | запрос (внутри E2E-сессии) | `APP_ACK` | 5 |
| `0x21` | `APP_ACK` | ответ | — | 5 |
| `0x70` | `ECHO_REQUEST` | диагностика: эхо кадра переменной длины | `ECHO_RESPONSE` | 1 |
| `0x71` | `ECHO_RESPONSE` | ответ | — | 1 |
| `0x7F` | `ERROR` | ответ на запрос либо уведомление | — | 1 |

`TUNNEL_DATA`, `TUNNEL_ACK`, `TUNNEL_CLOSE` не являются RPC: у каждой ячейки свой случайный
`request_id`, сопоставление — по `tunnel_id` и `seq`.

## 4. Сериализация payload

MessagePack (`msgpack` 1.x, `use_bin_type=True`). Ограничения распаковщика: строка ≤ 16 КиБ,
`bin` ≤ 64 КиБ, массив ≤ 64 элементов, map ≤ 32 пар, глубина ≤ 6, ключи — только строки,
ext-типы запрещены (никакой десериализации объектов языка). При кодировании ключи map
сортируются, целые кодируются минимальным представлением — одинаковые данные дают одинаковые
байты на всех узлах (это используется в подписях и в транскрипте рукопожатия).

### 4.1. Сравнение форматов

Замер `scripts/bench_serialization.py` (Python 3.10.11, медиана по повторам, реальные сообщения
протокола). Время — мкс на одно кодирование / декодирование.

| Сообщение | JSON (+base64) | MessagePack | CBOR (`cbor2`, канонический) |
|---|---|---|---|
| `PING` | 247 Б; 12,6 / 11,6 | **177 Б; 2,0 / 1,5** | 177 Б; 13,5 / 3,7 |
| `FIND_NODE_RESPONSE` (3 контакта) | 931 Б; 43,2 / 36,1 | **658 Б; 4,8 / 3,8** | 658 Б; 40,2 / 9,9 |
| `STORE_REQUEST` (NodeRecord) | 698 Б; 30,8 / 24,2 | **491 Б; 3,2 / 3,5** | 491 Б; 53,2 / 8,7 |
| `TUNNEL_DATA` (32 КиБ) | 43 772 Б; 276,8 / 177,6 | **32 812 Б; 3,4 / 2,4** | 32 811 Б; 11,0 / 4,2 |

JSON не имеет двоичного типа: ключи, подписи и ячейки туннеля приходится кодировать base64
(+33 %), и ячейка 48 КиБ после base64 уже не помещается в `MAX_FRAME_PAYLOAD`. CBOR даёт тот же
размер, что MessagePack, но его библиотека в 3–16 раз медленнее при кодировании. Protocol Buffers
требует генерации кода и отдельного описания схемы; строгая схема здесь задаётся в
`protocol/messages.py`. Выбран **MessagePack**.

## 5. Схемы payload

Обозначения: `bytes[n]` — ровно `n` байт, `bytes≤n` — не более `n`, `str≤n` — строка UTF-8,
`uN` — беззнаковое целое. Поля, которых нет в схеме, запрещены; необязательные поля помечены `?`.

**Contact** (сетевое представление контакта):

```text
Contact { node_id: bytes[32], identity_algorithm: "ed25519", identity_public_key: bytes[32],
          host: str≤253 (≥1), port: u16 }
```

Получатель контакта проверяет: `node_id == SHA-256(canonical_encode(identity_public_key))`,
ключ — корректная точка Ed25519, `host` — IPv4/IPv6 или имя хоста, `1 ≤ port ≤ 65535`, контакт —
не сам получатель. Метки `last_seen_ms` / `last_verified_ms` — локальные и по сети не передаются.

| Тип | Payload |
|---|---|
| `PING` | `{sender: Contact, timestamp_ms: u64}` |
| `PONG` | `{responder: Contact, ping_timestamp_ms: u64, responder_timestamp_ms: u64}` — `ping_timestamp_ms` повторяет значение из PING |
| `FIND_NODE_REQUEST` | `{sender: Contact, target_node_id: bytes[32]}` |
| `FIND_NODE_RESPONSE` | `{responder: Contact, target_node_id: bytes[32], contacts: [Contact] (≤ K_BUCKET_SIZE)}` |
| `STORE_REQUEST` | `{sender: Contact, key: bytes[32], record: NodeRecord}` |
| `STORE_RESPONSE` | `{responder: Contact, key: bytes[32], stored: bool, reason: str≤64}` |
| `FIND_VALUE_REQUEST` | `{sender: Contact, key: bytes[32]}` |
| `FIND_VALUE_RESPONSE` | `{responder: Contact, key: bytes[32], record?: NodeRecord, contacts: [Contact]}` — либо запись, либо ближайшие контакты |
| `SECURE_HELLO` | `{node_id: bytes[32], certificate: bytes≤2048 (DER), nonce: bytes[16], purpose: "link" \| "e2e"}` |
| `SECURE_HELLO_ACK` | `{node_id: bytes[32], certificate: bytes≤2048, nonce: bytes[16]}` |
| `TUNNEL_BUILD` | `{tunnel_id: bytes[16], sender: Contact, hop_index: u8, max_hops: u8, ttl_s: u32, remaining: [Contact] (≤16)}` |
| `TUNNEL_BUILD_OK` | `{tunnel_id: bytes[16], confirmations: [Confirmation] (1..17)}` |
| `TUNNEL_BUILD_FAIL` | `{tunnel_id: bytes[16], reporter: bytes[32], reason: str≤128, failed_node_id?: bytes[32]}` |
| `TUNNEL_DATA` | `{tunnel_id: bytes[16], seq: u64, data: bytes≤60000}` |
| `TUNNEL_ACK` | `{tunnel_id: bytes[16], seq: u64}` |
| `TUNNEL_CLOSE` | `{tunnel_id: bytes[16], reporter: bytes[32], reason: str≤128, failed_node_id?: bytes[32]}` |
| `APP_MESSAGE` | `{message_id: bytes[16], sender_node_id: bytes[32], recipient_node_id: bytes[32], timestamp_ms: u64, kind: "text", body: str≤16384}` |
| `APP_ACK` | `{message_id: bytes[16], status: "delivered" \| "duplicate" \| "rejected", received_at_ms: u64}` |
| `ECHO_REQUEST`, `ECHO_RESPONSE` | `{data: bytes≤65000}` |
| `ERROR` | `{code: str≤64, message: str≤256}` |

```text
Confirmation { node_id: bytes[32], hop_index: u8, prev_node_id: bytes[32],
               next_node_id: bytes[32], signature: bytes[64] }
```

Примеры кадров в байтах (PING, PONG, FIND_NODE, STORE, ...) — [docs/protocol_examples.md](docs/protocol_examples.md).

## 6. Kademlia DHT

### 6.1. Идентичность, XOR-метрика, k-bucket

```text
canonical_encode(pk) = ASCII("ed25519") || 0x00 || pk_raw(32 байта, RFC 8032)
NodeID               = SHA-256(canonical_encode(pk))          — 256 бит
distance(a, b)       = int(a) XOR int(b)                       — 256-битное целое без знака
bucket_index(a, b)   = номер старшего единичного бита distance(a, b), 0..255
```

Таблица — 256 bucket; bucket `i` хранит контакты с расстоянием в `[2^i, 2^(i+1))`, ёмкость
каждого — `K_BUCKET_SIZE = 3`. Внутри bucket контакты упорядочены от наименее недавно
подтверждённого (голова) к самому свежему (хвост). Эталонные векторы — `test_vectors/`.

Правила обновления при непосредственном наблюдении контакта (ответ на наш запрос или входящий
запрос):

| Ситуация | Действие |
|---|---|
| контакт есть, тот же ключ и адрес | обновить время, переместить в хвост |
| контакт есть, другой ключ при том же `NodeID` | отклонить (`route.reject`), таблица не меняется |
| контакт есть, другой адрес | проверить новый адрес PING'ом с ожидаемым `NodeID`; при успехе — обновить |
| нет, bucket не полон | добавить в хвост |
| нет, bucket полон | PING головному (LRU) контакту: ответил → он в хвост, новый отбрасывается; не ответил → LRU удаляется, новый добавляется в хвост |

Контакты из `FIND_NODE_RESPONSE` в таблицу напрямую не добавляются — только как кандидаты
текущего поиска; в таблицу узел попадает, когда сам ответит. Неудачный RPC увеличивает счётчик
отказов только этого контакта; после `CONTACT_MAX_FAILS = 2` подряд он удаляется.

### 6.2. Обработка FIND_NODE и FIND_VALUE

Ответчик проверяет контакт отправителя (§5), добавляет его в таблицу по правилам §6.1 и
возвращает до `k` уникальных контактов своей таблицы по неубыванию расстояния до цели, исключая
себя и запросившего. При TLS заявленный `sender.node_id` обязан совпадать с `NodeID`,
аутентифицированным в рукопожатии, иначе `ERROR IDENTITY_MISMATCH`.

`FIND_VALUE`: если у ответчика есть действительная запись по ключу (или ключ — его собственной
записи), возвращается `record`, иначе — ближайшие контакты, как в `FIND_NODE`.

Инициатор проверяет ответ: тот же `target_node_id`/`key`, `responder.node_id` равен
ожидаемому, число контактов ≤ `K_BUCKET_SIZE`, каждый контакт проходит проверку §5
(некорректные отбрасываются по одному), дубликаты удаляются.

### 6.3. Итеративный lookup

Вход: цель `T` (NodeID или ключ записи), вид поиска (`node` / `value`).

1. Кандидаты — `k` ближайших к `T` контактов собственной таблицы. Каждый кандидат имеет
   состояние `new → inflight → ok | failed`.
2. **Окно** `W` — `k` ближайших к `T` кандидатов, не помеченных `failed`.
3. Итерация: выбрать до `ALPHA = 3` кандидатов из `W` в состоянии `new` (ближайшие первыми),
   отправить им запросы параллельно и дождаться всех ответов или тайм-аутов.
4. Ответивший — `ok`; его контакты, которых ещё нет среди кандидатов и которые не равны
   инициатору, добавляются как `new`. Не ответивший (тайм-аут, отказ соединения, ошибка
   протокола) — `failed` и больше не опрашивается.
5. Если живых кандидатов меньше `k`, пул пополняется следующими по близости контактами
   своей таблицы.
6. **Остановка**: в окне `W` не осталось кандидатов `new` — все `k` ближайших живых
   кандидатов уже ответили, и опрос более дальних не может улучшить результат. Также поиск
   останавливается, если пул исчерпан или достигнут предел `MAX_LOOKUP_ITERATIONS = 32`.
7. Результат `FIND_NODE` — `k` ближайших ответивших; успех — цель среди ответивших.
   Для `FIND_VALUE` собираются все действительные копии записи, включая копию в собственном
   хранилище инициатора (она проверяется так же, как копия из сети), выбирается копия с наибольшим
   `sequence_number`; успех — найдена хотя бы одна действительная копия.

Отсутствие прогресса (ответы не приносят новых ближайших) приводит к остановке по п. 6, потому
что новых кандидатов `new` в окне не появляется. Повторный кандидат (уже известный `NodeID`)
игнорируется. Каждый lookup пишется в `lookups.jsonl`: `lookup_id`, инициатор, цель,
опрошенные узлы по итерациям, число RPC и итераций, тайм-ауты и ошибки, результат,
длительность, была ли цель в таблице до поиска, промежуточные узлы.

### 6.4. Bootstrap

- Первый (seed) узел запускается с пустым `BOOTSTRAP_PEERS`; пустая таблица для него допустима.
- Новый узел: PING каждому адресу из `BOOTSTRAP_PEERS` (`host:port` или `NodeID@host:port`;
  во втором случае ответ другого `NodeID` отклоняется) → self-lookup собственного `NodeID` →
  refresh bucket дальше ближайшего непустого → публикация своей записи (§7).
- Узел считается присоединившимся, если в таблице есть хотя бы один контакт.
- После присоединения bootstrap-узел для поиска не нужен: lookup использует только таблицу.

### 6.5. Refresh

Каждые `REFRESH_INTERVAL_S = 60 с` для каждого bucket, начиная с индекса на единицу ниже
ближайшего непустого и до 255, в котором не было поиска и изменений дольше интервала,
выполняется lookup случайного идентификатора из диапазона этого bucket.

## 7. Записи DHT

### 7.1. Формат NodeRecord

```text
NodeRecord { node_id: bytes[32], identity_algorithm: "ed25519", identity_public_key: bytes[32],
             addresses: [{host, port}] (1..4), sequence_number: u64,
             issued_at: u64, expires_at: u64, signature: bytes[64] }

key            = SHA-256("node:" || node_id)                      — упрощённый уровень, поиск по NodeID
signing_bytes  = "overlay-noderecord-v1" || 0x00 ||
                 msgpack([node_id, identity_algorithm, identity_public_key,
                          [[host, port], ...], sequence_number, issued_at, expires_at])
signature      = Ed25519.sign(identity_private_key, signing_bytes)
```

Порядок полей в подписываемом массиве фиксирован; сериализация детерминирована (§4).

### 7.2. Проверка перед сохранением и использованием

По порядку: схема; размер ≤ `MAX_RECORD_BYTES = 1024`; корректный Ed25519-ключ;
`node_id == SHA-256(canonical_encode(pk))`; запись лежит под своим ключом
(`key == SHA-256("node:" || node_id)`); подпись; `issued_at` не в будущем (допуск 30 с);
`expires_at > now`; `0 < expires_at − issued_at ≤ 300 с`; формат каждого адреса.

### 7.3. Конфликты и откат

Хранитель помнит максимальный `sequence_number` по каждому ключу (и после истечения записи):

| Пришло | Результат `STORE_RESPONSE` |
|---|---|
| номер больше сохранённого | запись заменяется, `stored=true, reason=STORED` |
| тот же номер, те же байты | обновляется время, `stored=true, reason=SAME` |
| тот же номер, другое содержимое | `stored=false, reason=SEQ_CONFLICT` |
| номер меньше максимального | `stored=false, reason=ROLLBACK` |
| запись не прошла §7.2 | `stored=false, reason=<код проверки>` (`SIGNATURE`, `EXPIRED`, `NODE_ID`, ...) |

При `FIND_VALUE` из нескольких копий выбирается копия с наибольшим `sequence_number`.

### 7.4. STORE, TTL, republish, репликация

- Владелец создаёт запись с TTL `RECORD_TTL_S = 180 с` и новым `sequence_number`
  (монотонный счётчик в `record_seq.json`, переживает перезапуск).
- `put_record`: lookup ключа → `STORE` трём ближайшим (`R = 3`); не ответившие заменяются
  следующими по близости. Успех — не менее `STORE_MIN_ACKS = 2` подтверждений.
- Переопубликование — каждые `REPUBLISH_INTERVAL_S = 90 с` (≤ TTL/2) с новым номером; если
  подтверждений было меньше `R`, повтор через 5 с.
- Передача записей новому узлу (как в §2.5 статьи Kademlia): когда узел впервые узнаёт о контакте
  (добавляет его в таблицу либо видит, что bucket полон), и этот контакт входит в `R` ближайших к
  ключу хранимой записи (среди контактов таблицы, самого узла и нового контакта), ему сразу
  отправляется `STORE` этой записи; одна версия записи одному узлу передаётся один раз. Без этого узлы, присоединившиеся после публикации и
  оказавшиеся ближе к ключу, не имели бы записи до переопубликования, а поиск, сходящийся на них,
  не находил бы её (дефект, выявленный в первой экспериментальной серии).
- Хранитель раз в секунду удаляет истёкшие записи. Хранилище сохраняется в `storage.json`;
  при загрузке каждая запись проверяется заново.
- Владелец отвечает на `FIND_VALUE` своего ключа собственной записью.

## 8. Защищённая сессия (TLS 1.3, взаимная аутентификация)

Используется для каждого межузлового TCP-соединения (`purpose = "link"`) и для end-to-end
сессии поверх туннеля (`purpose = "e2e"`).

```text
Инициатор I                                        Ответчик R
  SECURE_HELLO {node_id_I, cert_I, nonce_I, purpose}   ──►   (открытый кадр)
                                                           проверка: ключ cert_I — Ed25519,
                                                           SHA-256(canonical_encode(pk)) == node_id_I,
                                                           node_id_I ≠ свой, purpose ожидаемый
  (открытый кадр)   ◄──   SECURE_HELLO_ACK {node_id_R, cert_R, nonce_R}
  проверка: node_id_R == ожидаемому (если известен),
  ключ cert_R хэшируется в node_id_R
  ════════════ TLS 1.3 handshake (ClientHello ... Finished) ════════════
  каждая сторона доверяет ровно одному сертификату — закреплённому сертификату собеседника
  после рукопожатия: версия == TLSv1.3, сертификат собеседника побайтно равен закреплённому
  ── внутри TLS: T = SHA-256("overlay-hello-transcript-v1" || payload(HELLO) || payload(ACK)) ──►
  ◄── внутри TLS: T ──   (несовпадение → разрыв: подмена открытых HELLO-кадров)
  session_id = SHA-256("overlay-session-v1" || nonce_I || nonce_R)[:16]
  далее — кадры §2 внутри TLS
```

Параметры TLS-контекста: `minimum_version = maximum_version = TLSv1_3` (TLS 1.2 и ниже
отключены), `OP_NO_TICKET` (нет билетов возобновления → нет 0-RTT), `verify_mode = CERT_REQUIRED`
на обеих сторонах (mTLS), `check_hostname = False` (вместо имени проверяется `NodeID`),
`load_verify_locations(cadata = сертификат собеседника)`. Самоподписанный сертификат
принимается не потому, что он самоподписан, а потому что его ключ хэшируется в
ожидаемый/заявленный `NodeID`, а владение закрытым ключом доказывает подпись `CertificateVerify`.

Защита от повторов: внутри сессии — номера записей TLS (повтор или перестановка записи ломает
AEAD); между сессиями — новые эфемерные ключи ECDHE в каждом рукопожатии, поэтому записи
завершённой сессии не расшифровываются в новой. Прикладная дедупликация — `message_id` (§10).

## 9. Туннели

Туннель — последовательность различных узлов `I → R1 → R2 → D` (упрощённый уровень:
`TUNNEL_RELAYS = 2` ретранслятора). Ретрансляторы выбираются случайно из таблицы инициатора,
исключая получателя и узлы из списка исключений.

### 9.1. Построение

1. `I` создаёт `tunnel_id` (16 случайных байт) и отправляет `R1` запрос
   `TUNNEL_BUILD {tunnel_id, sender=I, hop_index=1, max_hops, ttl_s, remaining=[R2, D]}`.
2. Узел, получивший BUILD, проверяет: `sender` совпадает с аутентифицированным собеседником
   канала; `tunnel_id` ему не известен (повтор — признак петли); в `remaining` нет повторов и
   отправителя; `hop_index + len(remaining) ≤ min(max_hops, TUNNEL_MAX_HOPS)`;
   `0 < ttl_s ≤ TUNNEL_TTL_S`. Нарушение → `TUNNEL_BUILD_FAIL {reason}`.
3. Ретранслятор подключается к `remaining[0]` (TLS, ожидаемый `NodeID`) и пересылает ему
   `TUNNEL_BUILD` с `hop_index + 1` и укороченным `remaining`. Недоступен следующий узел →
   `TUNNEL_BUILD_FAIL {failed_node_id = следующий}`; отказ нижележащего узла передаётся вверх.
4. Получатель (`remaining = []`) создаёт конечную точку и отвечает `TUNNEL_BUILD_OK` с
   одним подтверждением; каждый ретранслятор на обратном пути добавляет своё:

```text
confirm_bytes = "overlay-tunnel-confirm-v1" || 0x00 || tunnel_id || node_id ||
                u8(hop_index) || prev_node_id || next_node_id        (у получателя next = 32 нулевых байта)
signature     = Ed25519.sign(identity_key, confirm_bytes)
```

5. `I` проверяет, что подтверждений столько же, сколько узлов пути, и каждое совпадает с
   запрошенным маршрутом (узел, номер хопа, соседи) и подписано ключом этого узла. Только тогда
   туннель `ACTIVE`; маршрут пишется в журнал (`tunnel.active route=...`). Ошибка построения —
   до 3 попыток, отказавший узел исключается.

### 9.2. Передача и контроль

- Данные инициатора режутся на ячейки `TUNNEL_DATA` по `TUNNEL_CELL_BYTES = 32 КиБ`, `seq`
  растёт на 1. Ретранслятор пересылает ячейку на другую сторону, определяя направление по
  соединению, из которого она пришла, и не изменяет её.
- Получатель на каждую прямую ячейку отвечает `TUNNEL_ACK {seq}`, ретрансляторы передают ACK
  к инициатору. Обратные данные получатель отправляет своими ячейками со своим `seq`.
- При простое инициатор раз в `TUNNEL_PROBE_INTERVAL_MS = 1000` шлёт пустую ячейку-зонд.
- Состояния инициатора:

| Состояние | Переход |
|---|---|
| `BUILDING` | создан, ждёт `TUNNEL_BUILD_OK` |
| `ACTIVE` | все подтверждения проверены; ACK приходят вовремя |
| `DEGRADED` | ACK не пришёл за `TUNNEL_ACK_TIMEOUT_MS = 2000`; следующий ACK возвращает `ACTIVE` |
| `CLOSING` | закрывается по запросу приложения или по истечении `TUNNEL_TTL_S` |
| `DEAD` | `TUNNEL_DEAD_AFTER_MISSES = 2` пропуска подряд, `TUNNEL_CLOSE` от соседа или разрыв канала к первому хопу |

### 9.3. Закрытие и отказ

Ретранслятор, потерявший соединение с соседом, отправляет в другую сторону
`TUNNEL_CLOSE {reason, failed_node_id = потерянный сосед}`; закрытие распространяется по цепочке.
Инициатор переводит туннель в `DEAD` и, если с получателем шла переписка, строит новый туннель,
исключая `failed_node_id` (при отказе, обнаруженном по тайм-ауту ACK, виновник неизвестен —
исключаются все ретрансляторы погибшего туннеля), затем устанавливает новую E2E-сессию.
Прямой доставки в обход туннеля нет.

## 10. Прикладные сообщения

1. Разрешение получателя: `FIND_VALUE(SHA-256("node:" || NodeID))` → проверенная запись (§7.2)
   → адрес и ключ.
2. Туннель (§9) и E2E-сессия: `SECURE_HELLO` и TLS 1.3 (`purpose = "e2e"`) идут байтами внутри
   ячеек туннеля; получатель проверяет, что ключ инициатора хэшируется в заявленный `NodeID`,
   инициатор — что отвечает ожидаемый получатель.
3. Внутри E2E-сессии — кадры §2: `APP_MESSAGE` → `APP_ACK`.
4. `message_id` — 16 случайных байт. Получатель проверяет `sender_node_id` == `NodeID` E2E-собеседника,
   `recipient_node_id` == свой, размер ≤ `MESSAGE_MAX_BYTES`. Пара (`sender_node_id`, `message_id`)
   запоминается (и сохраняется на диск); повтор подтверждается `APP_ACK status=duplicate`
   без повторного прикладного действия.
5. Нет `APP_ACK` за `MESSAGE_ACK_TIMEOUT_MS` или туннель погиб → повтор с тем же `message_id`
   по новому туннелю, всего до `MESSAGE_MAX_ATTEMPTS = 4` попыток.

## 11. Коды ошибок

| Код | Значение |
|---|---|
| `BAD_VERSION`, `UNKNOWN_TYPE`, `BAD_FLAGS`, `FRAME_TOO_LARGE` | нарушение заголовка кадра |
| `DECODE_ERROR`, `SCHEMA_ERROR` | payload не разбирается или не соответствует схеме |
| `BAD_DIRECTION`, `UNEXPECTED_RESPONSE` | ответ не на тот запрос либо без запроса; запрос без обработчика |
| `IDENTITY_MISMATCH` | заявленный `NodeID` не совпадает с аутентифицированным или ожидаемым |
| `INVALID_CONTACT` | контакт не прошёл проверку §5 |
| `INVALID_RECORD`, `ROLLBACK` | запись не прошла проверку §7.2; попытка отката |
| `TUNNEL_REFUSED` | отказ в построении туннеля |
| `INTERNAL` | внутренняя ошибка обработчика (без подробностей) |
