# Отчёт по этапам 1–2

**Тема:** «Защищённая оверлейная сеть передачи данных на основе пиринговых протоколов».
**Исполнитель:** Вихарев Д.А., группа ИСБ-123. **Уровень выполнения:** упрощённый.
**Данные контрольного запуска:** [`results/stage12-20261026-045354/`](../results/stage12-20261026-045354/)
(команда `python scripts/stage12_demo.py`, версия кода `902f68c`).

## 1. Проектное решение

| Параметр | Значение | Обоснование |
|---|---|---|
| Уровень | упрощённый | продвинутому нужны Docker/namespaces/`nftables` и `tc netem`, их нет на рабочей машине (Windows 11) |
| `N` | 15 | рекомендуемый диапазон 12–15; при `N = 10` в пилоте половина узлов знала всех (9 = N−1), при `N = 15` — ни один |
| `K_BUCKET_SIZE`, `ALPHA` | 3, 3 | значения упрощённого уровня |
| `NODE_ID_BITS` | 256 | SHA-256 |
| Язык | Python 3.10, asyncio | TLS 1.3 в стандартной библиотеке (`ssl`), один поток событий на узел без гонок данных |
| Библиотеки | `cryptography` (Ed25519, X.509), `msgpack` (сериализация), `pytest`, `matplotlib` | DHT, кадрирование и lookup реализованы самостоятельно |
| Развёртывание | независимые процессы на `127.0.0.1`, у каждого свой порт, ключ, таблица, журнал | Docker на машине нет; раздел 14 ТЗ допускает независимые процессы |

Ресурсы (замер на стенде из 15 узлов с TLS): рабочий набор одного процесса-узла 32–33 МБ,
из них собственной памяти около 20 МБ; все 15 узлов — около 0,5 ГБ, что укладывается в 16 ГБ
рабочей машины.

Прогноз заполнения таблиц: при случайных 256-битных `NodeID` каждый из остальных `N − 1 = 14`
узлов попадает в bucket 255 с вероятностью 1/2, в 254 — 1/4 и т. д.; bucket вмещает не более
`k = 3`. Если узел знает всех, кто помещается, ожидаемое заполнение bucket `255 − j` равно
`E[min(3, Bin(14, 2^−(j+1)))]`: 2,99; 2,60; 1,63; 0,86; 0,44; 0,22; … — в сумме **8,97 контакта**,
заметно меньше `N − 1 = 14`, то есть DHT при `N = 15, k = 3` не вырождается. Пилот (п. 7) и
итоговая серия это подтвердили: средний размер таблицы 9,1 (star) и 8,8 (ring), заполнение
старших bucket 3,0; 2,6; 1,8; 0,8 (star) и 3,0; 2,5; 1,7; 0,8 (ring).

## 2. Формат кадра

Заголовок 24 байта, порядок байтов сетевой (`struct "!BBH16sI"`):

| Поле | Размер | Назначение |
|---|---:|---|
| `version` | 1 | версия протокола, `1` |
| `type` | 1 | тип сообщения (`PING = 0x01`, `PONG = 0x02`, `FIND_NODE_REQUEST = 0x03`, `FIND_NODE_RESPONSE = 0x04`, `ERROR = 0x7F`, диагностический `ECHO 0x70/0x71`) |
| `flags` | 2 | в версии 1 зарезервировано, равно 0 |
| `request_id` | 16 | случайные байты `os.urandom`, ответ повторяет `request_id` запроса |
| `payload_length` | 4 | длина payload, не более `MAX_FRAME_PAYLOAD = 65536` |

Декодер потоковый: накапливает байты и выдаёт кадр только после получения заголовка и payload
целиком. Длина проверяется сразу после 24 байт заголовка — завышенная длина отклоняется
(`ERROR FRAME_TOO_LARGE`, закрытие соединения) до приёма payload. Неверная версия, неизвестный
тип, ненулевые флаги, ошибка схемы payload и ответ без ожидающего запроса тоже дают
документированный `ERROR` и закрытие соединения; сервер продолжает работу. Полная таблица —
[PROTOCOL.md §2](../PROTOCOL.md#2-формат-кадра).

## 3. Формат сериализации

Выбран MessagePack; сравнение на реальных сообщениях (`scripts/bench_serialization.py`):

| Сообщение | JSON (+base64) | MessagePack | CBOR (`cbor2`) |
|---|---|---|---|
| `PING` | 247 Б, 12,6 мкс | **177 Б, 2,0 мкс** | 177 Б, 13,5 мкс |
| `FIND_NODE_RESPONSE`, 3 контакта | 931 Б, 43,2 мкс | **658 Б, 4,8 мкс** | 658 Б, 40,2 мкс |

(время — кодирование одного сообщения, медиана). JSON требует base64 для ключей и подписей
(+33 % к размеру), CBOR даёт тот же размер, но медленнее при кодировании. Схемы payload строгие:
неизвестные поля и ext-типы MessagePack отклоняются, длины всех полей ограничены.

## 4. NodeID и контакт

```text
canonical_encode(pk) = ASCII("ed25519") || 0x00 || pk_raw      (32 байта, RFC 8032)
NodeID               = SHA-256(canonical_encode(pk))
```

Ключ Ed25519 создаётся при первом запуске и хранится в `NODE_STATE_DIR/identity_ed25519.pem`;
при перезапуске загружается, поэтому `NodeID` не меняется (тест T2.1). Контакт в сети —
`{node_id, identity_algorithm, identity_public_key, host, port}`; получатель заново вычисляет
`NodeID` из ключа и отклоняет несовпадение (T2.3, T2.4). Эталонные векторы — `test_vectors/`.

## 5. Таблица маршрутизации

256 bucket, bucket `i` хранит контакты с XOR-расстоянием в `[2^i, 2^(i+1))`, ёмкость каждого —
`k = 3`. Внутри bucket контакты упорядочены от наименее недавно подтверждённого к самому свежему.
Новый контакт попадает в таблицу только после непосредственного общения с ним (ответ на запрос
или входящий запрос); контакты из чужих `FIND_NODE_RESPONSE` используются лишь как кандидаты
поиска. Если bucket полон, наименее недавний контакт проверяется PING: ответил — остаётся,
новый отбрасывается (T2.8); не ответил — вытесняется (T2.9). Тот же `NodeID` с другим ключом
отклоняется, со сменой адреса — проверяется PING.

## 6. Bootstrap и lookup

```text
  узел i                      bootstrap-узел (1)                 остальные узлы
    │ PING ──────────────────────►│                                    │
    │◄─────────────────── PONG ───│   (оба добавляют друг друга)       │
    │ FIND_NODE(свой NodeID) ────►│                                    │
    │◄──── k ближайших контактов ─│                                    │
    │ FIND_NODE(свой NodeID), до ALPHA параллельно ───────────────────►│
    │◄───────────────────────────────────────── k ближайших ──────────│
    │ ... пока все k ближайших живых кандидатов не ответят (self-lookup)
    │ refresh: FIND_NODE случайного ID в каждом bucket дальше ближайшего соседа
```

Итеративный lookup: кандидаты — `k` ближайших контактов своей таблицы; на каждой итерации
опрашиваются до `ALPHA = 3` неопрошенных из окна `k` ближайших живых кандидатов; не ответившие
помечаются отказавшими; поиск завершается, когда все `k` ближайших живых кандидатов ответили.
Подробно — [PROTOCOL.md §6.3](../PROTOCOL.md#63-итеративный-lookup).

этап 2 — T2.1–T2.14 (сохранение идентичности, векторы NodeID и XOR, правила k-bucket, PING/PONG

многошаговый lookup отсутствующей цели, lookup после остановки bootstrap-узла). Все проходят.

**Этап 1, два процесса** (`stage1/`): серверы на портах 9401 и 9402; исходящее соединение
установлено, RTT 0,56 мс; PING и PONG с одинаковым `request_id = 4760c4c1…`; 100 кадров ECHO
длиной 0–47 317 байт (всего 467 747 байт) — получено 100 правильных ответов; два кадра одной

заголовка), принят целиком; заголовок с `payload_length = 65537` без payload — `ERROR FRAME_TOO_LARGE`
и закрытие соединения (журнал узла B: `protocol.error ... code=FRAME_TOO_LARGE`).

**Этап 2, 15 процессов, схема star, без TLS:**

- seed-узел запущен без bootstrap-контактов; каждый из узлов 2–15 выполнил PING узлу 1 и
  self-lookup (1–7 RPC, 1–3 итерации), присоединение заняло 10–41 мс на узел (`bootstrap_log.csv`);
- после сходимости таблицы содержат 7–10 уникальных контактов при `N − 1 = 14`: у **100 %**
  узлов меньше `N − 1` (требуется ≥ 80 %); ни один bucket не превышает `k = 3`
  (`routing_tables.json`, `routing_tables.csv`). Пример — узел 1: 9 контактов,
  bucket 255 — 3, 254 — 2, 253 — 1, 252 — 2, 251 — 1;

  `e0b34f37, e7de7482, ead740dc`, итерация 2 — `f138df36, f1e5b35e`; найдено, 5 RPC, 2 итерации,
  4,1 мс, 4 промежуточных узла, контакт цели вернул `e0b34f37`;
- 12 контрольных lookup с отсутствующей у инициатора целью: **12/12** успешны, 4–6 RPC, по 2 итерации,

## 8. Ограничения

- Все узлы на одном компьютере: задержки сети близки к нулю, измеренные времена отражают
  обработку в узлах. Схемы `star` и `ring` — схемы начального подключения, а не физические
  топологии: IP-достижимость между процессами полная.
- На Windows подключение к закрытому порту на `127.0.0.1` отклоняется примерно через 2 с
  (стек повторяет SYN), поэтому отказ узла обнаруживается не быстрее этого времени.
- Каналы этапов 1–2 открыты (`SECURITY_MODE=plain`); защита — этап 4.
