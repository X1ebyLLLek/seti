# Технические требования к этапам 1–2 курсовой работы

## Защищённая оверлейная сеть передачи данных на основе пиринговых протоколов

**Версия документа:** 1.0  
**Этапы:** 1 — транспорт и кадрирование; 2 — криптографическая идентичность, Kademlia DHT и bootstrap  
**Статус:** обязательные требования к реализации и промежуточной аттестации

---

## 1. Назначение документа

Документ определяет технические требования к двум первым этапам курсовой работы по разработке узла защищённой оверлейной P2P-сети. Требования обязательны для упрощённого и продвинутого уровней выполнения, если различие не указано явно.

Результатом этапов должен быть исполняемый программный прототип, в котором независимые узлы:

- обмениваются кадрами прикладного протокола поверх TCP;
- имеют устойчивую криптографическую идентичность;
- поддерживают ограниченную таблицу маршрутизации Kademlia;
- выполняют операции `PING` и `FIND_NODE`;
- присоединяются к сети через bootstrap-узел;
- выполняют итеративный поиск цели, которая отсутствовала в исходной таблице маршрутизации инициатора.

Этапы 1–2 не включают хранение значений (`STORE`, `FIND_VALUE`), TLS/AKE, туннели, прикладные сообщения и передачу файлов. Однако интерфейсы и формат сообщений должны быть спроектированы так, чтобы эти функции можно было добавить на последующих этапах без изменения базовой архитектуры.

---

## 2. Обязательная терминология

В исходном коде, отчёте, журналах и демонстрации используются следующие термины.

| Термин | Определение |
|---|---|
| **Узел** | Независимый логический экземпляр программы со своим `NodeID`, TCP-портом, каталогом состояния, таблицей маршрутизации и журналом |
| **Underlay-сеть** | Реальная IP-достижимость между процессами или контейнерами |
| **Bootstrap-узел** | Узел, чей адрес заранее известен новому участнику и используется только для первоначального входа в overlay |
| **DHT-overlay** | Логический граф контактов, хранящихся в таблицах маршрутизации узлов |
| **Контакт** | Проверяемая информация о другом узле: `NodeID`, адрес, порт и метаданные последнего наблюдения |
| **k-bucket** | Ограниченный по ёмкости список контактов заданного диапазона XOR-расстояний |
| **Lookup** | Итеративный поиск узлов, ближайших к целевому `NodeID`, через DHT RPC |
| **RPC** | Запрос прикладного протокола и соответствующий ему ответ, связанные полем `request_id` |

В общей Docker bridge-сети все узлы могут быть IP-достижимы друг для друга. В таком случае «звезда» и «кольцо» на этапах 1–2 означают только **схемы начального подключения**, а не физические топологии сети.

# Этап 1. Транспорт, кадрирование и диспетчеризация сообщений

## 3. Цель этапа 1

Реализовать транспортную подсистему P2P-узла: TCP-сервер, исходящие TCP-подключения, собственный двоичный формат кадров, сериализацию полезной нагрузки, диспетчеризацию по типу сообщения и базовую обработку ошибок протокола.

TCP является обязательным транспортом этапов 1–2. UDP добавляется позднее расширение и не заменяет обязательную реализацию TCP.

## 4. Структура проекта

Проект должен быть разделён не менее чем на следующие логические модули:

```text
transport/      TCP-соединения, чтение/запись, кадрирование, тайм-ауты
protocol/       константы версии, типы сообщений, кодеки заголовков и payload
identity/       ключи, NodeID, загрузка и сохранение состояния
routing/        XOR-метрика, Contact, k-bucket, RoutingTable
rpc/            обработчики PING/PONG и FIND_NODE
node/           запуск узла, конфигурация, bootstrap и координация подсистем
tests/          unit-, integration- и negative-тесты
scripts/        запуск демонстрации и автоматизированных проверок
```

Допускается иная структура при сохранении разделения ответственности. Прикладные обработчики не должны самостоятельно читать байты из TCP-сокета или разбирать заголовок кадра.

## 5. Конфигурация узла

Каждый узел принимает параметры из файла конфигурации, переменных окружения или аргументов командной строки. Минимальный набор параметров:

| Параметр | Требование | Пример |
|---|---|---|
| `NODE_STATE_DIR` | Индивидуальный каталог состояния узла | `./state/node-01` |
| `LISTEN_HOST` | IP-адрес привязки TCP-сервера | `0.0.0.0` |
| `LISTEN_PORT` | TCP-порт узла | `9101` |
| `BOOTSTRAP_PEERS` | Список начальных контактов, может быть пустым только у первого seed-узла | `node-01:9101` |
| `NODE_ID_BITS` | Фиксированное значение `256` | `256` |
| `K_BUCKET_SIZE` | `3` для упрощённого и `4` для продвинутого уровня | `3` |
| `ALPHA` | Параллелизм итеративного поиска, фиксированное значение `3` | `3` |
| `CONNECT_TIMEOUT_MS` | Тайм-аут установления TCP-соединения | `3000` |
| `READ_TIMEOUT_MS` | Тайм-аут ожидания данных в операции RPC | `5000` |
| `PING_TIMEOUT_MS` | Тайм-аут ответа `PONG` | `5000` |
| `MAX_FRAME_PAYLOAD` | Максимальная длина полезной нагрузки, `65536` байт | `65536` |
| `PROTOCOL_VERSION` | Версия прикладного протокола | `1` |
| `LOG_LEVEL` | Уровень диагностического журналирования | `INFO` |

Значения параметров, использованные в демонстрации, должны быть сохранены вместе с журналами. Изменение `K_BUCKET_SIZE` и `ALPHA` не должно требовать изменения исходного кода.

## 6. TCP-транспорт

### 6.1. Общие требования

Узел обязан:

- принимать входящие TCP-соединения на `LISTEN_HOST:LISTEN_PORT`;
- устанавливать исходящие соединения по адресу, содержащемуся в контакте;
- обслуживать несколько соединений без блокирования обработки остальных узлов;
- применять `CONNECT_TIMEOUT_MS` при установлении соединения;
- применять `READ_TIMEOUT_MS` при ожидании кадра или RPC-ответа;
- корректно закрывать соединение при разрыве, тайм-ауте или нарушении протокола;
- освобождать связанные с соединением ресурсы;
- фиксировать в журнале причину отказа, не выводя закрытые ключи и полное содержимое будущих защищённых сообщений.

Допускается создавать новое TCP-соединение для каждого RPC либо переиспользовать соединения. Выбранный подход должен быть описан в `ARCHITECTURE.md` и одинаково применяться в демонстрационном сценарии.

### 6.2. Ограничения

Не допускаются:

- предположение, что один вызов `read()` возвращает ровно один кадр;
- предположение, что один вызов `write()` соответствует одному чтению получателем;
- выделение памяти под payload до проверки `payload_length`;
- бесконечное ожидание ответа;
- завершение всего процесса из-за ошибочного входящего кадра от одного удалённого узла;
- передача объектных структур языка программирования в виде небезопасной сериализации, допускающей выполнение кода при десериализации.

## 7. Формат кадра (предлагаемый)

Каждый кадр передаётся в следующем двоичном формате. Все многобайтные целые числа кодируются в сетевом порядке байтов, big-endian.

| Смещение | Поле | Размер | Тип | Требование |
|---:|---|---:|---|---|
| 0 | `version` | 1 байт | unsigned integer | Должно быть равно `PROTOCOL_VERSION` |
| 1 | `type` | 1 байт | unsigned integer | Тип сообщения из таблицы раздела 8 |
| 2 | `flags` | 2 байта | unsigned integer | На этапах 1–2 равно `0`; резерв для следующих этапов |
| 4 | `request_id` | 16 байт | unsigned integer/UUID bytes | Уникален для инициируемого RPC в пределах процесса |
| 20 | `payload_length` | 4 байта | unsigned integer | От `0` до `MAX_FRAME_PAYLOAD` включительно |
| 24 | `payload` | переменно | bytes | Сериализованные данные сообщения |

Размер заголовка фиксирован и равен 24 байтам.

`request_id` в запросе генерируется криптографически стойким генератором случайных чисел. Ответ должен содержать тот же `request_id`, что и соответствующий запрос. Узел обязан отклонять ответ, не соответствующий ожидаемому запросу, либо относить его к отдельному входящему сообщению только если это допустимо типом протокола.

## 8. Типы сообщений этапов 1–2

| Код | Имя | Направление | Назначение |
|---:|---|---|---|
| `0x01` | `PING` | запрос | Проверка доступности и объявление контакта отправителя |
| `0x02` | `PONG` | ответ | Подтверждение доступности узла |
| `0x03` | `FIND_NODE_REQUEST` | запрос | Поиск контактов, ближайших к `target_node_id` |
| `0x04` | `FIND_NODE_RESPONSE` | ответ | Список ближайших известных контактов |
| `0x7F` | `ERROR` | ответ/уведомление | Ошибка протокола или обработки запроса |

Коды `0x05–0x3F` резервируются для следующих этапов. Самовольное изменение кодов после первой контрольной точки не допускается без повышения версии протокола.

## 9. Сериализация payload

Для payload допускаются JSON, MessagePack, CBOR, Protocol Buffers либо иной безопасный детерминированный формат. Формат должен удовлетворять требованиям:

- однозначно кодировать все поля сообщения;
- проверять типы и обязательность полей при декодировании;
- ограничивать размеры строк, массивов и вложенных структур;
- не принимать неиспользуемые поля без документированного правила;
- не использовать небезопасную десериализацию объектов;
- быть единообразным для всех узлов одной версии протокола.

В `PROTOCOL.md` студент обязан зафиксировать выбранный формат и привести минимум по одному примеру payload для `PING`, `PONG`, `FIND_NODE_REQUEST`, `FIND_NODE_RESPONSE` и `ERROR`.

### 9.1. Обязательные payload

`PING`:

```text
{
  sender: Contact,
  timestamp_ms: uint64
}
```

`PONG`:

```text
{
  responder: Contact,
  ping_timestamp_ms: uint64,
  responder_timestamp_ms: uint64
}
```

`FIND_NODE_REQUEST`:

```text
{
  sender: Contact,
  target_node_id: bytes[32]
}
```

`FIND_NODE_RESPONSE`:

```text
{
  responder: Contact,
  target_node_id: bytes[32],
  contacts: Contact[]
}
```

`ERROR`:

```text
{
  code: string,
  message: string
}
```

Набор `contacts` в `FIND_NODE_RESPONSE` не должен содержать более `K_BUCKET_SIZE` записей, если в проектной документации не обосновано и не согласовано другое ограничение. Все возвращаемые контакты сортируются по возрастанию XOR-расстояния до `target_node_id`.

## 10. Обработка некорректных кадров

Узел обязан закрыть входящее соединение после фиксации одного из следующих нарушений:

- неизвестная версия протокола;
- `payload_length > MAX_FRAME_PAYLOAD`;
- невозможность декодировать payload;
- payload не соответствует схеме указанного типа;
- сообщение с недопустимым направлением;
- разрыв TCP-соединения до получения полного заголовка или payload;
- нарушение обязательной корреляции `request_id` в ожидаемом RPC-ответе.

При возможности узел перед закрытием отправляет `ERROR`, но отправка `ERROR` не обязательна, если заголовок не может быть достоверно разобран или соединение уже разорвано.

Код ошибки не должен включать стек вызовов, путь к файлам, закрытые ключи, секреты или неконтролируемо длинные данные от удалённой стороны.

## 11. Диспетчеризация

После успешного разбора кадра транспорт передаёт объект сообщения диспетчеру. Диспетчер выбирает обработчик только по значению `type` и не должен содержать логику Kademlia.

Минимальные интерфейсы должны быть эквивалентны следующим:

```text
encode_frame(message) -> bytes
decode_frame(byte_stream) -> Frame | NeedMoreData | ProtocolError
dispatch(frame, connection_context) -> Response | NoResponse
send_request(contact, message, timeout) -> Response | RpcError
```

Реализация может использовать другой синтаксис, но должна обеспечивать такую же разделённость обязанностей.

## 12. Требования к журналированию этапа 1

Для каждого события фиксируются как минимум время, уровень, локальный `NodeID` в сокращённом виде, направление и идентификатор соединения либо RPC.

Обязательные события:

- старт TCP-сервера;
- исходящее подключение и его результат;
- входящее подключение;
- получение и отправка кадров с указанием `type`, `request_id`, размера и результата обработки;
- тайм-аут;
- ошибка декодирования;
- закрытие соединения и причина.

Полный payload сообщений в журнал не записывается по умолчанию. Режим расширенной диагностики допускается только при явном включении и не должен записывать закрытые ключи.

## 13. Приёмочные испытания этапа 1

### 13.1. Автоматические тесты

Должны быть реализованы не менее следующих тестов (хотя бы вручную):

| № | Испытание | Условие успешного прохождения |
|---:|---|---|
| T1.1 | Кодирование и декодирование корректного кадра | Все поля совпадают с исходными |
| T1.2 | Частичный заголовок | Декодер не создаёт сообщение до получения всех 24 байтов заголовка |
| T1.3 | Частичный payload | Декодер не создаёт сообщение до получения payload целиком |
| T1.4 | Склеенные кадры | Два и более кадра из одного чтения разбираются в правильном порядке |
| T1.5 | Кадры произвольного разбиения | Поток из 100 кадров корректно разбирается при случайном разбиении на фрагменты |
| T1.6 | Превышение длины | Кадр с `payload_length = MAX_FRAME_PAYLOAD + 1` отклоняется до выделения payload-буфера |
| T1.7 | Неизвестная версия | Соединение отклоняется либо возвращается документированная ошибка |
| T1.8 | Неизвестный тип | Соединение либо сообщение отклоняется документированным способом |
| T1.9 | Разрыв внутри кадра | Не создаётся частично заполненное сообщение; ресурсы освобождаются |
| T1.10 | Корреляция RPC | Ответ с другим `request_id` не принимается как ответ на ожидающий запрос |

### 13.2. Демонстрация преподавателю

На двух независимых узлах должны быть показаны:

1. Запуск TCP-сервера на разных портах.
2. Установление исходящего соединения одного узла с другим.
3. Обмен `PING`/`PONG` с одинаковым `request_id`.
4. Передача не менее 100 кадров переменной длины.
5. Корректная обработка склеенного и разделённого кадра.
6. Отклонение завышенной длины payload.
7. Журнал событий, подтверждающий результаты.

# Этап 2. Идентичность, таблица Kademlia, PING, FIND_NODE и bootstrap

## 14. Цель этапа 2

Реализовать криптографически связанную идентичность узла, ограниченную таблицу маршрутизации Kademlia, операции `PING` и `FIND_NODE`, присоединение через bootstrap-узел и итеративный поиск узла в сети.

На данном этапе DHT используется только для поиска узлов. Хранение и поиск произвольных значений добавляются на следующем этапе.

## 15. Криптографическая идентичность

### 15.1. Алгоритм и хранение

Каждый узел при первом запуске создаёт долговременную пару ключей Ed25519. Допускается другой современный алгоритм подписи, если он обоснован и поддерживается проверенной библиотекой.

Обязательные требования:

- закрытый identity-ключ генерируется криптографически стойким генератором;
- закрытый ключ сохраняется только в `NODE_STATE_DIR` данного узла;
- закрытый ключ не хранится в репозитории, образе контейнера, журналах, тестовых фикстурах и открытых конфигурациях;
- при повторном запуске из того же каталога узел использует ту же пару ключей и тот же `NodeID`;
- разные узлы в эксперименте используют разные пары ключей;
- для каждого экземпляра тестовой сети создаётся новый набор ключей либо явно документируется изолированный тестовый набор.

### 15.2. Формирование NodeID

`NodeID` имеет размер 256 бит и вычисляется следующим образом:

```text
NodeID = SHA-256(canonical_encode(identity_public_key))
```

`canonical_encode(identity_public_key)` должен быть однозначно определён: указывается алгоритм, формат, порядок байтов и способ сериализации ключа. Представление `NodeID` в логах и интерфейсе допускается в hex либо base32, но сравнение выполняется по 32 байтам исходного значения.

Не допускаются:

- случайный `NodeID`, не связанный с публичным ключом;
- ручное задание произвольного `NodeID` без проверки соответствия ключу;
- изменение `NodeID` при перезапуске при неизменном каталоге состояния.

### 15.3. Проверка контакта

Полученный контакт считается структурно допустимым только при выполнении всех условий:

- `node_id` имеет длину 32 байта;
- `identity_public_key` имеет корректный формат;
- `SHA-256(canonical_encode(identity_public_key)) == node_id`;
- адрес и порт имеют допустимый формат;
- контакт не ссылается на локальный узел как на удалённый;
- общий размер сериализованного контакта не превышает документированное ограничение.

На этапах 1–2 публичный ключ передаётся в составе контакта без подписи транспортного сообщения. Криптографическая аутентификация удалённой стороны и защита от MITM реализуются на следующем этапе. В отчёте обязательно указать, что этап 2 не предоставляет защищённый канал и не устраняет MITM-угрозу.

## 16. Формат контакта

Каждый контакт имеет следующую логическую структуру:

```text
Contact {
  node_id: bytes[32],
  identity_algorithm: string,
  identity_public_key: bytes,
  host: string,
  port: uint16,
  last_seen_ms: uint64,
  last_verified_ms: uint64
}
```

Поля `last_seen_ms` и `last_verified_ms` являются локальными метаданными и не должны приниматься от удалённого узла как достоверные. В сетевом payload допускается передавать только необходимые адресные и идентификационные поля; после приёма узел самостоятельно устанавливает локальные временные метки.

Для этапов 1–2 адрес контакта состоит из одного TCP-адреса. Поддержка нескольких адресов, IPv6, NAT traversal и relay не требуется.

## 17. XOR-метрика

Для `NodeID` длиной 256 бит расстояние определяется как:

```text
xor_distance(a, b) = integer_from_big_endian(a XOR b)
```

где `a` и `b` — 32-байтовые `NodeID`.

Сравнение расстояний выполняется как сравнение беззнаковых 256-битных чисел. Нельзя использовать знаковые преобразования, десятичное строковое сравнение, лексикографическое сравнение hex-строк разной длины или хэширование уже сформированного `NodeID` перед вычислением расстояния.

## 18. Таблица маршрутизации

### 18.1. Общая организация

Таблица маршрутизации строится из k-bucket, покрывающих пространство XOR-расстояний относительно локального `NodeID`.

Допускаются две реализации:

- фиксированные 256 bucket по индексам старшего установленного бита XOR-расстояния;
- динамическое разбиение bucket по классическому правилу Kademlia.

Выбранный вариант должен быть описан в `ARCHITECTURE.md`. Независимо от варианта должны выполняться все требования данного раздела.

Каждый bucket имеет максимальную ёмкость `K_BUCKET_SIZE`. Для упрощённого уровня используется `K_BUCKET_SIZE = 3`, для продвинутого — `K_BUCKET_SIZE = 4`.

### 18.2. Порядок контактов и обновление

Контакты в bucket упорядочиваются по времени последнего успешного наблюдения: наименее недавно подтверждённый контакт располагается первым, наиболее недавно подтверждённый — последним.

При получении валидного сообщения от удалённого узла либо успешном получении корректного `PONG`:

1. Контакт проверяется по правилам раздела 15.3.
2. Если контакт уже есть в bucket, его адресные данные актуализируются, а контакт перемещается в конец bucket.
3. Если контакт отсутствует и bucket не заполнен, контакт добавляется в конец bucket.
4. Если контакт отсутствует и bucket заполнен, выполняется `PING` наименее недавно подтверждённого контакта.
5. Если проверяемый контакт не отвечает за `PING_TIMEOUT_MS`, он удаляется, а новый контакт добавляется в конец bucket.
6. Если проверяемый контакт отвечает, он перемещается в конец bucket, а новый контакт не добавляется.

Запрещается вытеснять живой контакт без проверки только потому, что новый контакт имеет меньшее расстояние до локального узла.

### 18.3. Дубликаты и конфликты

- Один `NodeID` может присутствовать в таблице маршрутизации не более одного раза.
- Контакт с тем же `NodeID`, но иным открытым ключом отклоняется как нарушение идентичности.
- Контакт с тем же `NodeID` и иным адресом допускается обновить только после успешной проверки доступности по новому адресу или по документированному правилу anti-spoofing.
- Локальный `NodeID` не помещается в собственную таблицу маршрутизации.

## 19. Операция PING

### 19.1. Назначение

`PING` используется для проверки доступности контакта, подтверждения адресной информации и обслуживания LRU-порядка k-bucket.

### 19.2. Обработка запроса

Получив `PING`, узел обязан:

1. Проверить корректность заголовка и payload.
2. Проверить структуру контакта отправителя.
3. Обработать контакт отправителя в таблице маршрутизации по разделу 18.
4. Отправить `PONG` с тем же `request_id`.
5. Поместить в `PONG` собственный контакт и значение `ping_timestamp_ms`, полученное из запроса.

### 19.3. Обработка ответа

Инициатор принимает `PONG` только при выполнении условий:

- `request_id` совпадает с ожидающим `PING`;
- ответ получен до `PING_TIMEOUT_MS`;
- контакт ответчика структурно корректен;
- `node_id` ответчика совпадает с ожидаемым `NodeID`, если запрос направлялся конкретному контакту.

После успешного `PONG` контакт ответчика обновляется в таблице маршрутизации. Тайм-аут означает недоступность для данного испытания; он должен быть отражён в журнале и обработан согласно разделу 18.2.

## 20. Операция FIND_NODE

### 20.1. Обработка запроса

Получив `FIND_NODE_REQUEST`, узел обязан:

1. Проверить структуру запроса и контакта отправителя.
2. Обработать контакт отправителя в таблице маршрутизации.
3. Найти до `K_BUCKET_SIZE` известных контактов, ближайших к `target_node_id` по XOR-метрике.
4. Исключить из ответа повторяющиеся контакты и локальный контакт, если он не является документированно необходимым.
5. Отсортировать контакты по неубыванию XOR-расстояния до цели.
6. Вернуть `FIND_NODE_RESPONSE` с тем же `request_id` и исходным `target_node_id`.

Ответ может быть пустым, если у узла нет подходящих контактов. Отправка искусственно сгенерированных контактов, контактов из центрального реестра или полного списка всех узлов запрещается.

### 20.2. Валидация ответа

Получив `FIND_NODE_RESPONSE`, инициатор обязан:

- проверить соответствие `request_id` и `target_node_id` ожидающему запросу;
- проверить структуру контакта ответчика;
- проверить структуру каждого возвращённого контакта;
- удалить дубликаты по `NodeID`;
- не добавлять локальный `NodeID` как удалённый;
- не доверять `last_seen_ms`, переданному удалённой стороной;
- учитывать контакт ответчика как наблюдаемый только после корректного ответа;
- помещать новые контакты в пул кандидатов lookup и обновлять собственную таблицу согласно правилам bucket.

## 21. Итеративный FIND_NODE lookup

### 21.1. Входные данные

Операция имеет вид:

```text
lookup_node(target_node_id) -> LookupResult
```

где `LookupResult` содержит как минимум итоговый список ближайших известных контактов, флаг успеха, число RPC, число итераций, список тайм-аутов и длительность операции.

### 21.2. Алгоритм

Алгоритм обязан использовать `ALPHA = 3` параллельных запроса на итерацию.

1. Из таблицы маршрутизации выбираются до `K_BUCKET_SIZE` ближайших к цели контактов.
2. Кандидаты сортируются по XOR-расстоянию до цели.
3. На каждой итерации выбираются до `ALPHA` ещё не опрошенных ближайших кандидатов.
4. Выбранным кандидатам параллельно отправляются `FIND_NODE_REQUEST`.
5. Корректные ответы объединяются с текущим набором кандидатов; дубликаты удаляются.
6. Контакты с тайм-аутом или ошибкой фиксируются в результате; они не опрашиваются повторно в том же lookup, если не реализована и не документирована стратегия повторов.
7. Поиск продолжается, пока существует не опрошенный кандидат, который ближе к цели, чем ближайший уже полностью обработанный набор, либо пока не будут опрошены все известные релевантные кандидаты.
8. Поиск завершается, когда дальнейший опрос не может улучшить список ближайших `K_BUCKET_SIZE` контактов либо исчерпан пул кандидатов.

Конкретное условие остановки фиксируется в `PROTOCOL.md`, тестируется и применяется одинаково ко всем прогонам.

### 21.3. Запреты

Не допускаются:

- последовательный опрос всех узлов при `ALPHA = 3`, если это не вызвано недостатком кандидатов;
- прямой запрос к целевому адресу, полученному от тестового оркестратора;
- скрытая загрузка полного списка узлов;
- признание lookup успешным только потому, что все узлы заранее известны инициатору;
- удаление всех контактов по одному тайм-ауту без учёта состояния конкретного bucket.

## 22. Bootstrap

### 22.1. Первый узел

Первый seed-узел запускается с пустым `BOOTSTRAP_PEERS`. Его таблица маршрутизации изначально пуста. Это единственный случай, когда отсутствие bootstrap-контакта допускается без ошибки конфигурации.

### 22.2. Присоединение нового узла

Новый узел с непустым `BOOTSTRAP_PEERS` обязан выполнить:

1. Загрузку или создание identity-ключа и вычисление `NodeID`.
2. Установление TCP-соединения с хотя бы одним bootstrap-контактом.
3. `PING` bootstrap-узлу.
4. Добавление подтверждённого bootstrap-контакта в таблицу маршрутизации.
5. Итеративный `FIND_NODE` для собственного `NodeID`.
6. Сохранение итогового состояния таблицы маршрутизации и журнала bootstrap-процесса.

Bootstrap-узел не является центральным каталогом. После первоначального присоединения нормальная работа lookup не должна требовать его доступности.

### 22.3. Схемы начального подключения

На этапе 2 должны быть подготовлены конфигурации для двух схем:

- **Star bootstrap** — все новые узлы начинают присоединение через один seed-узел.
- **Ring bootstrap** — каждый очередной узел получает адрес предшествующего либо ближайшего уже запущенного узла по заданному порядку.

Для каждой схемы фиксируются: список начальных контактов, порядок запуска, задержка между стартами, время начала измерения и итоговое заполнение таблиц маршрутизации.

## 23. Журналирование этапа 2

В дополнение к журналам этапа 1 фиксируются:

- сокращённые идентификаторы локального и удалённого узлов;
- создание или загрузка identity-ключа без вывода закрытого ключа;
- вычисленный `NodeID`;
- добавление, обновление, проверка и вытеснение контакта;
- номер bucket и причина изменения;
- `PING`/`PONG` и RTT;
- `FIND_NODE`-запросы и ответы;
- идентификатор lookup, целевой `NodeID`, номер итерации, опрошенные кандидаты;
- число RPC, тайм-ауты, итоговые ближайшие контакты и длительность lookup;
- ход bootstrap: подключение, `PING`, self-lookup, итоговый размер таблицы.

Не допускается выводить в журнал закрытые ключи, сессионные секреты, значения генератора случайных чисел, используемые для ключей, либо неограниченные списки payload.

## 24. Автоматические тесты этапа 2

| № | Испытание | Условие успешного прохождения |
|---:|---|---|
| T2.1 | Устойчивость identity | После перезапуска с тем же `NODE_STATE_DIR` `NodeID` не меняется |
| T2.2 | Различие узлов | Два новых узла имеют разные `NodeID` |
| T2.3 | Связь ключа и ID | Из public key повторно вычисляется тот же `NodeID` |
| T2.4 | Подмена ключа | Контакт с несоответствующими `node_id` и public key отклоняется |
| T2.5 | XOR-метрика | Расстояние и сортировка контактов совпадают с эталонными тест-векторами |
| T2.6 | Вставка в неполный bucket | Новый валидный контакт добавляется в конец bucket |
| T2.7 | Повторное наблюдение | Известный контакт перемещается в конец bucket |
| T2.8 | Полный bucket, живой LRU | После успешного `PING` старый контакт сохраняется, новый не добавляется |
| T2.9 | Полный bucket, мёртвый LRU | После тайм-аута LRU удаляется, новый контакт добавляется |
| T2.10 | PING/PONG | Ответ имеет тот же `request_id`, контакт ответчика корректен |
| T2.11 | FIND_NODE sorting | Ответ содержит не более допустимого числа уникальных контактов, отсортированных по XOR-расстоянию |
| T2.12 | Bootstrap | Новый узел после `PING` и self-lookup имеет хотя бы один подтверждённый удалённый контакт |
| T2.13 | Многопереходный lookup | Инициатор находит контакт через промежуточный узел, не имея цели в исходной таблице |
| T2.14 | Отказ bootstrap | После завершённого присоединения отключение bootstrap-узла не делает невозможным контрольный lookup между ранее присоединившимися узлами |

Эталонные тест-векторы XOR-метрики, `NodeID` и сортировки контактов должны быть сохранены в репозитории в независимом от реализации формате.

## 25. Приёмочная демонстрация этапа 2

### 25.1. Минимальный стенд

До завершения этапа 2 демонстрируется сеть минимум из 5 одновременно работающих логических узлов. Для итогового эксперимента используется масштаб, выбранный по полному ТЗ:

- упрощённый уровень: рекомендуется `N = 12–15`, `K_BUCKET_SIZE = 3`;
- продвинутый уровень: рекомендуется `N = 20–21`, `K_BUCKET_SIZE = 4`.

Количество узлов выбирается студентом с обоснованием. До перехода к следующим этапам студент обязан показать пилотный запуск, подтверждающий, что система не использует полный каталог участников и что инициатор контрольного lookup не знает целевой узел заранее.

### 25.2. Обязательный сценарий

1. Запустить seed-узел без bootstrap-контактов.
2. Запустить остальные узлы согласно `star` либо `ring` bootstrap-схеме.
3. Для каждого нового узла показать `PING` bootstrap-узлу и self-lookup.
4. Дождаться завершения bootstrap всех узлов.
5. Выбрать пару «инициатор — цель» так, чтобы цель отсутствовала в таблице маршрутизации инициатора до начала lookup.
6. Запустить `lookup_node(target_node_id)`.
7. Показать по журналам и результату lookup, что были опрошены промежуточные узлы и что итоговый список содержит цель либо контакты, ближайшие к цели.
8. Показать число RPC, число итераций, длительность lookup и последовательность кандидатов.
9. Остановить bootstrap-узел.
10. Повторить контрольный lookup между двумя ранее присоединившимися узлами.

### 25.3. Требование невырожденности для контрольной точки

К завершению этапа 2 должны быть предоставлены:

- выгрузка таблиц маршрутизации всех узлов;
- число уникальных контактов в каждой таблице;
- заполнение каждого bucket;
- не менее 10 контрольных lookup на пилотной сети;
- для каждого lookup — факт отсутствия целевой записи у инициатора до запуска, число RPC и число итераций.

Демонстрация, в которой каждый узел знает всех остальных до начала поиска, не засчитывается как проверка DHT lookup.

## 27. Критические нарушения

Этапы 1–2 не принимаются до устранения хотя бы одного из следующих нарушений:

- TCP-приём реализован с предположением «одно чтение — один кадр»;
- отсутствует ограничение `MAX_FRAME_PAYLOAD` до выделения памяти;
- `request_id` не используется для корреляции запросов и ответов;
- `NodeID` не связан детерминированно с долговременным public key;
- закрытые ключи находятся в репозитории или образе контейнера;
- k-bucket не ограничены по ёмкости;
- новый контакт вытесняет живой LRU-контакт без `PING`;
- `FIND_NODE` возвращает центральный или заранее загруженный полный список участников;
- контрольный lookup выполняется для цели, уже известной инициатору;
- bootstrap-узел требуется для каждого поиска после завершения присоединения;
- отсутствуют автоматические тесты или журнал, позволяющий проверить этап.

## 28. Дальнейшее развитие

Архитектурные решения этапов 1–2 должны позволять на следующих этапах добавить:

- подписанные `NodeRecord` и операции `STORE`/`FIND_VALUE`;
- TTL, репликацию и переопубликование;
- TLS 1.3 с взаимной аутентификацией либо собственный AKE;
- end-to-end защиту прикладных данных;
- туннели через промежуточные узлы;
- механизм восстановления после отказов;
- экспорт метрик и автоматизацию экспериментальных серий.

Добавление этих возможностей не должно требовать изменения формата заголовка кадра версии 1 или переписывания базовой реализации `RoutingTable`.
